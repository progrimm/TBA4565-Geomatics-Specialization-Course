\section{3DGS Viewer: what is inside a Gaussian splat file?}\label{sec:p3}

\subsection{Question}

3D Gaussian splatting \citep{kerbl2023} has quickly become a popular way to capture real places in 3D from ordinary photos, and splat files are increasingly shared as if they were 3D models. For GIS use, the important questions are what such a file actually contains and whether it can be placed in the real world. The 3DGS Viewer is a static web page where you open your own splat file (PLY, SPZ, \code{.splat}, \code{.ksplat} or SOG) and inspect it: what it contains, which way is up, and how far apart two points are. The file is read in the browser and never uploaded. The project asks what a 3DGS file contains, and how well a static web page can open and inspect it entirely on the client.

\paragraph{How the project changed.} The first version (27--28 October) was a CesiumJS globe with a gallery of georeferenced splats from Cesium ion and Bentley iTwin, and a ``viewer lab'' comparing splat renderers. It was dropped on 28 October: the gallery's Cesium ion assets loaded only with Cesium's evaluation token, not with my own token; the iTwin share key expires on 1 December 2026; and Esri's sample layer states no licence. A public website cannot depend on any of these, so the project was rebuilt as a viewer for the user's own files. The earlier version remains in the repository history.

\subsection{Background}\label{sec:p3-background}

\paragraph{Gaussian splats.} A 3DGS scene is a set of 3D Gaussians, typically hundreds of thousands. Each has a mean position, a covariance (stored as a scale per axis and a rotation quaternion), an opacity and a colour that varies with viewing direction, expressed as spherical-harmonic (SH) coefficients \citep{kerbl2023}. To render a view, each Gaussian is projected to a 2D ellipse (a ``splat''), the splats are sorted by depth and alpha-blended. The Gaussians are fitted to the input photos with a photometric loss.

\paragraph{Splats, meshes and point clouds.} A mesh has explicit surfaces and topology, and a point cloud has surface samples without extent. A Gaussian has extent, orientation and transparency, but no surface: it is optimised to \emph{look} right from the training views, not to lie exactly on a surface. This matters for measurement: picking a point on a splat hits a semi-transparent ellipsoid, not a surface.

\paragraph{File formats.} The reference implementation writes a binary PLY file \citep{bourke-ply} with one record per Gaussian: position \code{x y z}, \code{scale\_0..2}, \code{rot\_0..3}, \code{opacity}, the base colour \code{f\_dc\_0..2} and the higher-order SH coefficients \code{f\_rest\_*}. The SH degree $d$ follows from the number of \code{f\_rest} properties, $3\left((d+1)^2-1\right)$, so degree~3 has 45. Compressed formats such as SPZ \citep{spz}, SOG \citep{playcanvas-sog} and \code{.ksplat} quantise these values to make files several times smaller.

\paragraph{Reference frames and georeferencing.} A splat inherits the coordinate frame of the structure-from-motion reconstruction it was trained from (for example COLMAP \citep{colmap}). That frame has an arbitrary origin and orientation, and an arbitrary scale unless the capture was scaled. Conventions also differ: 3DGS training output usually has $-Y$ up, while GIS and CAD data usually have $+Z$ up. To use a splat in GIS it must be georeferenced, for example with GNSS camera positions or ground control points, which gives a transformation to a CRS such as ECEF (EPSG:4978). Georeferenced splats can then be streamed onto a globe as 3D Tiles with the glTF \code{KHR\_gaussian\_splatting} extension \citep{khr-gaussian-splatting,3dtiles}. The viewer does none of this; it shows the file in its own frame, which is exactly what makes the gap visible.

\subsection{Data}

The app ships no data. Two files were used to test it:
\begin{itemize}
  \item \textbf{SOAR Telescope} by Luis Cerda \citep{soar}, CC BY 4.0: the SOAR telescope on Cerro Pachón, Chile, converted from a SuperSplat compressed PLY to a standard PLY with \code{splat-transform}~3.10.3. 200,258 Gaussians, 47,262,365 bytes. The header size plus $200{,}258 \times 59 \times 4$ bytes matches the file size exactly. It is used on the homepage screenshot, but is not hosted on the site.
  \item \textbf{Nugatti jar}: a splat of a Nugatti jar on a piece of burlap that I provided, exported from LichtFeld Studio v0.5.4 on 28 October 2026. 154,055 Gaussians. It was used for the figures in this section and is not published.
\end{itemize}

The viewer (\cref{fig:p3-arch}) is a static Vite and React app. Rendering uses Spark 2.4 \citep{spark}, a Gaussian-splat renderer on three.js \citep{threejs}, both MIT-licensed. The three.js objects live in one module outside React; the React components hold only interface state. The file is read with \code{File.arrayBuffer()} and the bytes go to two places: a small PLY header parser written for this project, and Spark's loader. The splat and the measurement markers sit in one parent group, so changing the up axis rotates both and measurements stay in file coordinates.

\subsection{Method}

Opening a file runs these steps:
\begin{enumerate}
  \item Check the file extension, read the file into memory and start a timer.
  \item For PLY files, parse the header: encoding, splat count, properties and SH degree. A PLY without the Gaussian properties (\code{scale\_*}, \code{rot\_*}, \code{opacity}, \code{f\_dc\_*}) is rejected as a mesh or plain point cloud.
  \item Let Spark decode the file. On an error, keep the previously opened splat.
  \item Collect all finite splat centres and compute two bounding boxes: the full box, and a \emph{core} box from the 2\,\% and 98\,\% quantiles on each axis. ``Floaters'', stray Gaussians far from the scene, are common in splat captures and would otherwise push the camera far away.
  \item Frame the camera on the core box (distance $= r/\sin(\text{fov}/2)$ for the bounding sphere radius $r$) and show the facts and the load time.
\end{enumerate}
The user can then switch the up axis between $+Y$, $-Y$, $+Z$ and $-Z$ (default $-Y$), and measure the straight-line distance between two picked points. Picking casts a ray through the pointer and takes the nearest splat ellipsoid it hits.

\paragraph{Orientation.} Neither file says which way is up. Both were upright with the default $-Y$, the usual convention for 3DGS training output, and wrong with the GIS convention $+Z$ (\cref{fig:p3-upaxis}). A GIS tool that assumes $+Z$ up would therefore show such a file lying on its side.

\paragraph{Measurement and scale.} \Cref{fig:p3-measure} measures across the lid of the Nugatti jar: 1.075 units. This is a distance in the file's own units. Nothing in the file says what a unit is, so without a known reference length the number cannot be turned into centimetres. This is the scale ambiguity of structure from motion, made concrete.

\paragraph{Cost of a client-only viewer.} The production bundle is 3,496\,kB of JavaScript (1,168\,kB gzipped), mostly Spark, and it must be downloaded before a file can be opened. In exchange there is no server, no token and no upload, and the viewer worked unchanged when deployed under a sub-path on GitHub Pages.

\subsection{Verification}

\begin{itemize}
  \item \textbf{Unit tests} (Vitest, 26 tests in 7 files) cover the pure helpers: the PLY header parser (3DGS headers, Windows line endings, plain point clouds, SuperSplat compressed PLY, non-PLY input), SH degree, the core and full bounds (including floaters and NaN centres), camera framing, the four up-axis rotations, distance and formatting. The rendering module, hooks and components need WebGL and are checked in the browser only.
  \item \textbf{Browser checks.} The SOAR file was opened three times in the production build with Playwright and gave identical facts and no console errors, and the facts were recomputed independently from the raw file. Error cases (a text file, a PLY with only \code{x y z}, a truncated PLY) were checked on 28 October: each shows a message and the open splat stays. The Nugatti figures were captured on the live site on 29 October with no console errors.
  \item \textbf{Review.} An automated code review found 10 issues, which were fixed before release.
\end{itemize}

\subsection{Limitations}\label{sec:p3-limits}

\begin{itemize}
  \item Only plain PLY was tested in a browser. Compressed PLY is recognised in unit tests only, and SPZ, \code{.splat}, \code{.ksplat} and SOG rely on Spark's loaders without being tested here. Formats other than PLY are recognised by file extension only.
  \item The whole file is held in memory; files much larger than 47\,MB were not tested.
  \item There is no real-world frame or scale, the up axis can only be changed in 90\dg{} steps, and multi-file formats and 3D Tiles tilesets cannot be opened.
  \item ``Extent'' is the box of splat \emph{centres}, so the visible object is somewhat larger, and the per-axis 96\,\% box can contain fewer than 96\,\% of all splats.
  \item Picking hits the nearest splat ellipsoid, and semi-transparent floaters can be hit first. Measuring needs a pointer and is not keyboard-accessible.
  \item Load times come from one machine in headless Chromium; they are not a benchmark.
\end{itemize}
