\section{Trondheim 3D: how far is the walk to the nearest public shelter?}\label{sec:p2}

\subsection{Question}

Norway's public shelters (\emph{tilfluktsrom}) are registered by the Norwegian Directorate for Civil Protection (DSB) and published as open data. A map can show where they are, but in an emergency the useful question is which shelter is closest \emph{on foot}, and how far that walk is. Trondheim 3D is a CesiumJS city model of Trondheim with terrain, 3D buildings and the public shelters. Clicking the ground finds the nearest shelter along the OpenStreetMap walking network and draws the route. The project is the GI-systems part of the module: most of the work lies in combining data from different sources and reference systems into one working 3D application.

\subsection{Background}\label{sec:p2-background}

\paragraph{Reference systems and heights.} The shelters are published in EUREF89 / UTM zone 32N (EPSG:25832), with easting and northing in metres. CesiumJS works in Earth-centred, Earth-fixed coordinates (EPSG:4978) and takes positions as WGS~84 longitude, latitude and \emph{ellipsoidal} height. The shelters are therefore converted to longitude/latitude when the data is prepared, treating EUREF89 as equal to WGS~84 (no datum shift). Heights need more care. Norwegian heights (NN2000) are measured above the geoid, which near Trondheim lies about 40\,m above the WGS~84 ellipsoid. The camera targets of the preset views are built from Kartverket's terrain height in NN2000 plus a fixed +40\,m. This fixed offset is an approximation, not a geoid model, so a height read from the app is not an NN2000 height.

\paragraph{Local frames for the camera.} Each preset view stores a landmark (from OpenStreetMap via Nominatim) and a heading, pitch and range. The camera offset is built in the landmark's local East-North-Up frame and converted to ECEF with \code{Transforms.eastNorthUpToFixedFrame} \citep{cesiumjs}, so the landmark is centred by construction.

\paragraph{3D Tiles and level of detail.} The buildings are Cesium OSM Buildings, streamed as 3D Tiles \citep{3dtiles}: a hierarchy of tiles at increasing detail. A tile is refined when its \emph{screen-space error}, the geometric error projected to pixels, exceeds \code{maximumScreenSpaceError} (default 16). A higher value loads fewer and coarser tiles.

\paragraph{Geodesic distance.} Straight-line distances and the edge lengths of the walking network are geodesics on the WGS~84 ellipsoid, computed with CesiumJS's \code{EllipsoidGeodesic}, which uses Vincenty's method \citep{vincenty1975}. The implementation is tested against GeographicLib, which implements Karney's algorithm \citep{karney2013,geographiclib}. Heights are ignored, so distances are measured on the ellipsoid surface.

\paragraph{Network analysis.} The walking network is modelled as a graph: OpenStreetMap nodes are vertices and way segments are undirected edges weighted by their geodesic length. The shortest walk is found with Dijkstra's algorithm \citep{dijkstra1959}. Because the search can stop at the first shelter it reaches, one search from the clicked point finds the nearest shelter by walking distance.

Two quality issues matter for the analysis. The shelter request uses a fixed $20\times20$\,km square around the city centre, not the municipal boundary, and whether it covers all of Trondheim municipality was not checked. The OpenStreetMap network is a volunteer-mapped snapshot, so a missing or mistagged path changes the result.

The app (\cref{fig:p2-arch}) is a static Vite and React application around CesiumJS 1.146 \citep{cesiumjs}. CesiumJS code lives in small plain-JavaScript modules, one per layer, so the Cesium API stays visible instead of being hidden behind a wrapper library. Every layer loads asynchronously with its own error handling: if one fails, the rest of the app keeps working and a message explains what is missing. The scene renders only when something changes (\code{requestRenderMode}). Clicking a shelter or a building opens Cesium's InfoBox with its attributes (\cref{fig:p2-infobox}).

There is no backend and no routing service. A hosted routing API (GraphHopper) was considered and rejected: its API key would be public in the browser bundle, and the free daily quota could run out. Instead the walking network is downloaded once as a static file and the graph is searched in the browser.

\subsection{Method}\label{sec:p2-method}

When the user clicks the ground:
\begin{enumerate}
  \item The camera ray through the clicked pixel is intersected with the terrain (\code{Globe.pick}), giving a WGS~84 position. A click on a building or a shelter opens its InfoBox instead.
  \item The click is snapped to the nearest network node. The shelters were snapped once, when the network loaded.
  \item A Dijkstra search with a binary heap runs from the click's node and stops at the first shelter node it reaches.
  \item The walking distance is the geodesic connector from the click to its node, plus the network path, plus the connector from the shelter's node to the shelter.
  \item The straight-line geodesic distance to the same shelter is computed for comparison. If the network failed to load, or no shelter is reachable, the app falls back to the nearest shelter in a straight line.
  \item The route is drawn as a line clamped to the ground, and the panel shows the shelter, its capacity, the walking distance and the straight-line distance.
\end{enumerate}

To see how much the walking network changes the answer, the same functions were run in Node over a $30\times30$ grid of points (cell centres) covering the shelters' bounding box. For each point, the walking-nearest shelter was compared with the straight-line-nearest shelter, and the ratio of walking to straight-line distance was recorded.

For the buildings layer, \code{maximumScreenSpaceError} values of 16 (the default) and 32 were compared with a Playwright benchmark: the Midtbyen view at $1600\times900$ in headless Chromium with the GPU enabled, three runs per value with a fresh browser context, measuring the time until all terrain and building tiles had loaded, the frame rate during a scripted 10\,s orbit, tile memory and JavaScript heap.

\paragraph{Shelters.} The study area has 12 public shelters with 5,268 places in total, from 45 to 800 places each. \Cref{fig:p2-overview} shows the start view with the shelters in the city centre.

\paragraph{Single clicks.} From Torvet, the main square, the nearest shelter is no.~6870, 199.3\,m away in a straight line (GeographicLib: 199.2548\,m) and 275.8\,m on foot. \Cref{fig:p2-route} shows a click south of the cathedral: the river is in the way, so the 490\,m straight line becomes a 684\,m walk over Gamle Bybro. Building the graph took 169\,ms and a single search a few milliseconds in Node (median 4.5\,ms over the 900 grid points), which is fast enough to answer each click immediately.

\paragraph{Walking versus straight line.} Over the 900 grid points:
\begin{itemize}
  \item a shelter was reachable from 884 points; from 16 points none was (probably disconnected parts of the network, not investigated);
  \item at 168 of the 884 reachable points (19.0\,\%), the shelter that is nearest on foot is \emph{not} the one that is nearest in a straight line;
  \item the walk to the nearest shelter is a median of 1.34 times the straight-line distance, and 1.68 times at the 90th percentile.
\end{itemize}
A straight-line ``nearest shelter'' map would therefore point to the wrong shelter at about one location in five, and a typical walk is about a third longer than the straight line suggests. The grid also covers water, where points snap to the nearest shore, so these numbers describe the method on this network rather than the population.

\paragraph{Level of detail.} \Cref{tab:p2-bench} shows the benchmark. Doubling the screen-space error to 32 saved a third of the tile memory, but did not improve the frame rate, which was close to the 60\,Hz display limit in both cases, and the first load was dominated by the network. Screenshots at 32 showed many small buildings missing in the centre, so the default of 16 was kept.

\subsection{Verification}

\begin{itemize}
  \item \textbf{Unit tests} (Vitest, 54 tests in 11 files). Geodesic distances agree with textbook WGS~84 values and with the GeographicLib reference to within 0.5\,mm. The network tests use a small hand-made river with one bridge, to check that Dijkstra goes round via the bridge, and cover unreachable targets and the straight-line fallback. The shelter parser is tested with valid and deliberately broken WFS responses, and the coordinate conversion with known UTM points. The camera tests check that the camera ends up exactly \code{range} metres from the target in the right direction.
  \item \textbf{Robustness.} A Playwright script loads the production build three times: normally, with the shelter file blocked, and with the network file blocked. In each case the app stays usable, shows an explanatory message, and (with the network blocked) falls back to straight-line distances. It passed again on 29 October 2026.
  \item \textbf{Accessibility.} A second script tabs through the panel at both widths with reduced motion and checks that every control has a visible focus outline and can be operated with the keyboard. Text contrast was computed with the WCAG formula from the style tokens (12.7:1 for body text, 5.7:1 for muted text) \citep{wcag-contrast}.
  \item \textbf{CI and deployment.} GitHub Actions runs lint, format check, tests and build. On the live site, the production Cesium ion token was accepted from the Pages origin (HTTP 200) and rejected from another origin (HTTP 403).
\end{itemize}

\subsection{Limitations}\label{sec:p2-limits}

\begin{itemize}
  \item Heights are ellipsoidal, and the +40\,m geoid offset for the camera targets is an approximation. EUREF89 is treated as WGS~84; the size of that difference was not computed in the project.
  \item The analysis ignores slope, stairs, barriers and opening hours, and it ignores capacity: it always picks the nearest reachable shelter, however full it would be.
  \item Clicks and shelters snap to the nearest network \emph{node}, not the nearest point on an edge, and the connectors are straight lines that can cross buildings or water.
  \item The shelter extract is a $20\times20$\,km square, not the municipality, and its completeness was not checked. OSM building completeness and heights depend on volunteer mappers and were not compared with Kartverket's FKB data.
  \item The search needs a map click, so it is not available from the keyboard. On a phone, the open control sheet covers the map credits.
  \item The benchmark covers one machine, one view and headless Chromium, with a frame rate capped by the display.
\end{itemize}
