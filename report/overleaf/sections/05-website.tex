\section{The website}\label{sec:website}

The three apps are published as one static website on GitHub Pages \citep{ghpages}. A build script builds the homepage and the three apps into one folder, and a GitHub Actions workflow publishes it every time the main branch changes. Each project also has its own workflow that runs code checks, unit tests and a build.

A static host can only serve files, which had three consequences:
\begin{itemize}
  \item Each app lives in its own sub-path, such as \code{/projection-lab/}, so every app loads its files with relative paths.
  \item Projection Lab cannot use its database and API on the website. In a static mode, the map instead reads two JSON files exported from the same database queries.
  \item The Cesium ion token for Trondheim 3D ends up in the public JavaScript code. It is stored as a secret in GitHub and added at build time, and in Cesium ion it is limited to read access from the website's address. A request with the token was accepted from the website's address and refused from another address.
\end{itemize}

\section{Challenges along the way}\label{sec:challenges}

\begin{itemize}
  \item \textbf{Data I could not use.} The first version of the 3DGS project showed example splats from Cesium ion and two other providers. The Cesium examples only loaded with Cesium's own evaluation token, not with my account, one dataset depended on a share key that expires in December 2026, and one had no stated licence. A public website cannot depend on that, so I rebuilt the project around local files. I should have checked access and licences before building on the data.
  \item \textbf{Invalid geometries.} Two countries in Natural Earth, the USA and Sudan, had self-intersecting boundaries. They were repaired with \code{ST\_MakeValid} in PostGIS before any areas were computed.
  \item \textbf{Poles and the antimeridian.} Antarctica reaches the pole, where Mercator is undefined, and Russia, Fiji and Antarctica are split at 180\dg{}. Both cases needed their own handling and tests in the area calculation.
  \item \textbf{Camera views.} The first preset views used guessed camera positions and missed their landmarks. Describing each view as a target with a direction and a distance solved this.
\end{itemize}

\section{Reflection}\label{sec:reflection}

In Projection Lab, computing the areas myself showed me why Mercator exaggerates the far north, and why a country's exaggeration depends on its whole extent and not only its latitude. Trondheim 3D was mostly about making data from different sources fit together: two coordinate systems, two kinds of height, a WFS service, OpenStreetMap and Cesium's streamed data. The 3DGS Viewer showed me that a splat looks impressive but carries less information than GIS data needs, since it has no position, orientation or scale in the real world.

Together, the projects gave me practice with a full web GIS stack, from PostGIS and Python on the server to D3, CesiumJS and three.js in the browser.

The AI assistant made it possible to finish three working apps in the time I had. The cost is that I wrote little of the code in the later projects myself, so there my learning came from deciding, reviewing and testing rather than from writing code. Besides the two rules in \cref{sec:work}, it helped to look at the screenshots myself instead of trusting a report that a page worked. In Projection Lab, two layout bugs were found that way: a tooltip covering its own point, and overlapping axis labels on narrow screens.

\section{Conclusion}\label{sec:conclusion}

In this report I have described three small web GIS projects. Projection Lab measures how much the Mercator projection inflates the area of each country and compares it with the theoretical $\sec^2\varphi$. Trondheim 3D combines terrain, buildings and DSB's public shelters in CesiumJS, and finds the nearest shelter along the walking network. The 3DGS Viewer opens Gaussian splat files in the browser and shows what they contain and what they lack as geodata. All three apps are published together on one website.
